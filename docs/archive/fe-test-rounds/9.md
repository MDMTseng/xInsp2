# Round 2 / 10 — FE happy path (FE-E2) + orphan guarantee (FE-E3)

## Planned this round
The two safety holes the crash-storm test can't cover: a healthy line that runs
+ shuts down cleanly, and the guarantee that a *supervisor* crash never orphans
the backend.

## Implemented
- `examples/fe_supervisor_healthy/` — same `raw_thread_crash` plugin but
  `config:{"armed":false}` (a never-crashing line), `counter` instance,
  `inspect.cpp`, `project.json`.
- `driver.py` with two phases:
  - **FE-E2**: autostart a healthy project, require it stays up untouched 8 s,
    `backend healthy` logged, **no** `BackendExit` safe-state, then Ctrl-Break →
    `SupervisorShutdown` + `supervisor stopping` + no orphan.
  - **FE-E3**: hard-`kill()` the FE (TerminateProcess, no ctrl handler) → assert
    the backend is reaped within 10 s (Job Object `KILL_ON_JOB_CLOSE`).
- Driver creates the FE in a new process group so it can send `CTRL_BREAK_EVENT`.

## Code change (found by testing)
**Observability fix in `fe_main.cpp`:** the monitor only logged `backend healthy`
/ cleared safe-state when it had *previously* been in safe state — so a
never-crashed healthy start emitted **no** positive liveness signal (silence =
healthy). Reworked the healthy-probe branch to:
- clear safe state only if `in_safe_state` (preserves SP4 — never clear
  optimistically), and
- announce `backend healthy` once per backend instance regardless.
This gave FE-E2 something to assert *and* improves real-world observability.

## Result
- `fe_supervisor_healthy` → **PASS** (both phases).
- `fe_supervisor` (crash storm) re-run after the monitor change → **PASS** (no
  regression: still logs respawn/ENTER/CLEAR/cap).

## Studied → new corner cases / findings for next rounds
1. **FE-E3 is the strongest result** — confirms a Python `proc.kill()` (hard
   TerminateProcess on the FE) still reaps the BE. Worth a harder variant:
   kill the FE *during* a respawn backoff window (BE not yet spawned) — does the
   job still hold? And kill via Task Manager / `taskkill /F /T`. (Round 7/10.)
2. **Autostart negatives untested**: what if the FE points at a project that
   doesn't compile, or a missing dir? Today the BE stays up (autostart logs the
   error) but the line never actually inspects — the FE sees a healthy *port*
   and reports healthy, so a **silently-broken line looks fine to the FE**. This
   is a real semantic gap: port-up ≠ inspecting. → Round 3 covers the BE-side
   autostart negatives (AS-I4/5/6); flag the FE-can't-tell-broken-line issue as
   a Phase-2 deep-heartbeat item.
3. **No timestamp in safe-state log** (carried from round 1) still open.
4. **Healthy window is wall-clock 8 s** — slowish. Acceptable for a regression
   but note it; could assert via a client reading `dispatch_stats` advancing
   instead of just "port stays up" to actually prove *inspecting*, not just
   *listening*. → candidate refinement (Round 6 with the recover test).
