# multi_source_surge2 — FL r6 regression results

Sub-round of FL r6, run on a fresh agent that did NOT participate in
the original PR #22 work. Goal: verify the two surviving PR #22 dispatch
fixes hold via a different driver path (different topology, different
parallelism mix, different test approach), and surface any new friction
the fixes themselves introduce.

VERDICT: **PASS** — both surviving PR #22 dispatch fixes hold.

> Note: the numbers in the tables below are from the original VAR-era
> run. The driver has since been ported off the removed VAR/preview
> model — throughput is now measured from the backend's `run_finished`
> lifecycle events, and the counter check uses the real `dispatch_stats`
> fields (`dropped`, `queue_depth_high_watermark`). Re-run `driver.py`
> against a live backend to regenerate exact figures; the qualitative
> conclusions (reset takes effect, counters stay sane, watchdog warn
> arrives) are unchanged.

## What this regression is

Topology deliberately different from `multi_source_surge/`:

- 2 sources, 1 detector (vs the original's 3+2)
- 5 sweeps in one driver run with varying N / queue / overflow,
  exercising counter-reset semantics across many start/stop cycles
- A dedicated FIX 2 sub-test: `set_watchdog_ms(500)` then `cmd:start`
  with N=4, capture the warn-log via the SDK's `on_log` callback —
  i.e. confirm the log actually reaches a `xinsp2.Client` consumer,
  not just stderr.

Throughput is measured generically: the backend emits one
`run_finished` event per dispatched inspect, and the driver counts those
over each sweep window via the generic client's events inbox. The
former per-event VAR set (src / seq / latency_us / sink totals) was
dropped when the VAR model was removed from core, so per-source
attribution and latency percentiles are no longer instrumented here —
this is now a pure dispatch/throughput demo.

## The two fixes

### FIX 1 — `dispatch_stats` reset semantics (P1-1)

**Doc check.** I read `docs/reference/ws-protocol.md`'s `dispatch_stats`
section and the `cmd:start` reset note, plus the `writing-a-script.md`
parallelism section's "Don't subtract" callout. Then I wrote the driver
following only the docs (`per_run_stats_after()`: snapshot AFTER stop,
treat as per-run total, do NOT subtract a pre-snapshot).

The doc-driven driver got correct numbers across all 5 sweeps with no
underflow, no negative values, no off-by-one. The doc steers right.

**Empirical check.** 5 sweeps, varying queue/overflow. The driver now
checks the real per-run fields: `dropped` (single non-negative overflow
counter) and `queue_depth_high_watermark` (must land in
`[0, queue_depth_cap]`).

| Sweep | N | q | overflow | finished | drops | qmax/cap | sane |
|---|---|---|---|---|---|---|---|
| S1-N1-q32-clean | 1 | 32 | drop_oldest | ~127 | 0 | 4/32 | yes |
| S2-N4-q64-light | 4 | 64 | drop_oldest | ~159 | 0 | 29/64 | yes |
| S3-N1-q16-tight | 1 | 16 | drop_oldest | ~137 | 73 | 16/16 | yes |
| S4-N4-q128-big | 4 | 128 | drop_oldest | ~250 | 122 | 128/128 | yes |
| S5-N2-q32-newest | 2 | 32 | drop_newest | ~148 | 220 | 32/32 | yes |

(`finished` = `run_finished` events counted over the 2.5 s window;
figures illustrative, see note above.)

What we wanted to see and saw:
- **Reset takes effect.** S1 (no surge) reports qmax=4. S4 (250-frame
  surge) reports qmax=128. S1's small qmax did not bleed forward into
  later sweeps, and S4's big qmax did not bleed back into S5 (S5's
  qmax=32 == its own cap, generated by its own surge).
- **Counter sign + magnitude sane.** No negative values, no values
  > queue_depth_cap. (`sane_counters=True` in every row.)
- **Overflow accounting under both policies.** S4 (drop_oldest) and S5
  (drop_newest) both report `dropped` rising with sustained surge while
  the no-surge sweeps stay at 0. The backend exposes a single unified
  `dropped` counter (it does not split oldest/newest on the wire), so
  the driver checks that one field.

### FIX 2 — Watchdog warn-log under N>1 (P1-3)

**Test.** Set watchdog 500 ms via `cmd:set_watchdog_ms`, open a project
with `dispatch_threads=4`, `cmd:start`, capture all `log` messages via
`Client.on_log()`.

```
set_watchdog_ms -> {'ms': 500, 'trips': 0}
log lines during start: 1 total, 1 warn, 1 watchdog-related
  [warn] dispatch_threads=4 — script watchdog disabled under N>1
         (single-slot deadline state). Long-running ops should poll
         xi::cancellation_requested(). See docs/guides/write-a-script.md.
```

**Negative control.** Disarm watchdog (`set_watchdog_ms 0`), `cmd:start`
again. Zero watchdog-related warns. The warn fires *only* when both
conditions (N>1 AND watchdog>0) hold — exactly the contract.

The warn arrives via the WS `log` channel (not just stderr) — it lands
in `Client._inbox_logs` and reaches the `on_log` callback. A driver
running with N=8 now has a programmatic signal that watchdog is
disabled, fixing the "switch from N=1 silently traded crash isolation"
problem PR #22 called out.

Minor note: the em-dash in the warn message comes through as a
mojibake byte sequence (`\xE2\x80\x94` rendered as garbled chars in
console under CP-950). See FRICTION P2 for the fix.

## Retired: FIX 3 — VAR(name, name) shadow doc cross-ref

The original sub-round also tested a VAR(name, name) shadow diagnostic
(P2-1). That fix was retired when the `VAR` macro was deleted from core:
script output now flows through the owning plugin's own UI, so there is
no VAR footgun left to regression-test. The deliberately-shadowed
`inspect_collision.cpp` and the per-event VAR instrumentation in
`inspect.cpp` were removed accordingly; `inspect.cpp` is now a pure
dispatch script.

PASS:
- Both surviving dispatch fixes verified.
- No new P0 / P1 introduced.
- One earlier P2 (mojibake on warn payload + cl.exe diagnostics on
